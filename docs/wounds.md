## Resolved wounds

### 2026-10-30 — The English home reached crawlers empty, and every made-up URL was an indexable page `bug`
- **Symptom:** measured on production with GPTBot's user agent (Organicus AI-readiness report, Enzo, 2026-10-30): `/` — the root and the `x-default` of every hreflang set — had 0 words, no H1 and no JSON-LD, while `/does-not-exist` got the full home with JSON-LD. `/pokemon/notreal` answered 200 as "Notreal: weaknesses, stats & builds", canonical to itself; `/llms.txt` answered 200 with the app's HTML.
- **Root cause:** two separate gaps. (1) Vercel serves a file that exists *before* it applies a rewrite, so `/` is `dist/index.html` itself and never reaches `api/render-meta.js` — only the root, which is why `/pt` was fine. (2) `render-meta` answered 200 for every path: an unknown route fell through to the home's meta, and an unknown Pokémon, team or type kept its slug as a name.
- **Fix:** (1) `scripts/lib/prerenderHome.mjs` (a Vite plugin) writes `buildPage(…, '/')` into `dist/index.html` at build time and saves the untouched template as `dist/shell.html`, which `render-meta` now reads (`X-Robots-Tag: noindex` on `/shell.html`, kept out of the precache). (2) `buildPage` decides existence: a path no route knows, or a Pokémon / tournament team / type / guide its data does not have, is a **404** with `noindex` and a "page not found" prerender; the visitor's own pages (`/profile`, `/teams`, `/battles`…) are 200 + `noindex`; a move/ability/item the dex cannot describe is 200 + `noindex`. Lookups only count as a miss when their data loaded.
- **Correct pattern:** a page that exists as a static file bypasses every rewrite — anything the function adds to pages must be baked into that file too. And a catch-all renderer must decide existence; "200 for everything" turns every typo and every bot probe into an indexable page.
- **Files:** `scripts/lib/prerenderHome.mjs`, `vite.config.js`, `api/render-meta.js`, `vercel.json`, `api/render-meta.test.js`

### 2026-10-29 — Gym teams never resolved a regional form ("Alolan Ninetales") `bug`

### 2026-10-29 — Cynthia's teams rail collapsed after visiting (or hovering) Friends/Battles `bug`
- **Symptom:** on desktop (≥1601px, Chrome and Firefox), the Champion Challenge's left rail ("Team of the day") came out ~286px tall beside an ~850px console, its rows squeezed to 13px with sprites and names overlapping. Only F5 fixed it.
- **Root cause:** a class-name collision between two lazy stylesheets. The rail (`ChallengeTeamsRail`, 2026-10-29) is `.challenge-teams`; the friend-battle `ChallengeModal` already used `.challenge-teams` for its team list, with `display: grid; max-height: 15rem; overflow-y: auto`. `challenge-modal.css` rides in the Friends and Battles chunks, which load when those screens open or their nav links are hovered (route prefetch) — from then on, for the rest of the session, the modal's `max-height: 15rem` capped the rail (no rule in the DS sheet resets max-height, so load order did not even matter). F5 dropped the stylesheet, so it "fixed itself". Headless runs that open `/challenge` directly never load the modal's CSS, which is why it would not reproduce.
- **Fix:** the modal's block is `.challenge-modal-teams` (its file's own prefix). Reproduced by importing `ChallengeModal.jsx` before mounting the room: card 254px / rows 13px before, 845px / 54px after.
- **Correct pattern:** lazy CSS is global once loaded — a class in a route's stylesheet must be namespaced by its file/component (`.challenge-modal-*`, `.ds-*`), never a generic block name another view could pick. Before naming a new block, `grep -rn "\.<name>\b" src/styles`. When a layout breaks "only on first visit" or "until F5", suspect a stylesheet some *other* route brought in, and reproduce by loading that route's chunk first.
- **Files:** `src/components/modals/ChallengeModal.jsx`, `src/styles/challenge-modal.css`

### 2026-10-29 — The Challenge ranking sheet could not scroll and sat under the dock (iPhone) `bug`
- **Symptom:** on an iPhone, "Today's ranking" showed its first rows, the dock covered the bottom (Streak/Wins/Days) and nothing in the sheet scrolled.
- **Root cause:** `ChallengeRankingSheet` rendered its `.modal-scrim` in place, inside `.challenge-view` — a size container (`container: challenge / inline-size`). Safari still applies layout containment to size containers, which makes the container the box `position: fixed` measures from and a stacking context of its own: the scrim was the page's size, not the screen's, and the dock (z 25 in the shell) drew over it. Chromium dropped that containment, so desktop Chrome and headless runs never show it.
- **Fix:** the sheet is `createPortal`led to `document.body`. Reproduced headless by adding `contain: layout style` to `.challenge-view`: in place, the scrim measured 292px from y=72 with the dock on top; portalled, it covers 844px and the list scrolls.
- **Correct pattern:** a dialog rendered inside a view that is a container-query container (or has `transform`, `filter`, `contain`) must portal to `<body>`. Test such bugs with `contain: layout` forced on — Chromium will not show them otherwise.
- **Files:** `src/components/views/challenge/ChallengeRanking.jsx`

### 2026-10-29 — The forum feed clipped its own edge-to-edge rows on phones `bug`
- **Symptom:** in the feed list, a framed avatar (`@alex`) lost the left side of its ring.
- **Root cause:** below 1024px the feed scroller and its rows reach past the page gutter with negative margins, but `.forum-view` and `.forum-center` are `overflow: hidden` and sit on the gutter, so they cut the reach at x=17 (ring started at x=12). Same family as the thread-avatar wound below.
- **Fix:** on phones both panes are `overflow-x: visible; overflow-y: clip` — they still hold their height, and `clip` (unlike `hidden`) leaves the other axis visible. `.forum-view .forum-center` because `.forum-center`'s own rule comes later in the file.
- **Correct pattern:** before reaching past a gutter with negative margins, list every ancestor up to the screen whose `overflow-x` is not `visible`. A pane that only needs to contain height should clip on Y alone.
- **Files:** `src/styles/forum-view.css`

### 2026-10-29 — The Home's chip strip never scrolled; it was cut at the screen edge `bug`
- **Symptom:** on a phone the Home's status chips ended in "League Ch" at the right edge and could not be swiped.
- **Root cause:** `.cozy-toolbar` is `flex-wrap: wrap` and turns into a column below 1024px. In a *wrapping* column flex container the line is as wide as its widest item's max-content, so `.cozy-chips` (overflow-x: auto) stretched to 553px inside a 356px toolbar — it never overflowed itself, so it never scrolled; the page cut it.
- **Fix:** `flex-wrap: nowrap` on the phone column; the strip now runs to the screen edge (into the gutter) and fades there with a mask, so the last chip reads as "swipe for more".
- **Correct pattern:** a horizontal scroller inside a `flex-direction: column` parent needs that parent to be `nowrap`. Check `el.scrollWidth > el.clientWidth` on the scroller itself — a scroller whose own box is as wide as its content is not scrolling.
- **Files:** `src/styles/cozy-home.css`

### 2026-10-29 — The logo focus ring was clipped or erased on core controls `bug`
- **Symptom:** tabbing the core pages, focus landed on the selected segment ("Today", "Rewards"), on profile/builder tabs, Home's chips, Pokédex card stars, phone builder cards and the composer's Save, and showed no ring or a ring cut on one to three sides; 65 controls still drew Tailwind's flat 2px Volt ring.
- **Root cause:** Neon Sticker's focus is a 6px outer `box-shadow` (`--ring-logo`). (1) The anchored segmented thumb sets the selected item's `box-shadow: none` after the focus rule; (2) `.tabs`, `.cozy-chips`, `.pokemon-card` and the composer fold clip overflow; (3) `.is-synergy`/`.is-suggested` card tints set their own inset shadow later than the card's focus rule; (4) `focus-visible:ring-2 ring-primary` utilities outrank the `:where()` focus rule.

Verified by a tab-through audit that walks each focused control's ancestors for clipping.
- **Correct pattern:** a new control inside `overflow: hidden`/`auto` uses `--ring-logo-inset`; a state rule that sets `box-shadow` on a focusable control must not land after its `:focus-visible` rule at equal specificity. Audit by tabbing, not by eye.
- **Files:** `src/index.css`, `src/styles/cozy-home.css`, `src/styles/pokemon-card.css`, `src/styles/team-builder-view.css`, `src/styles/app-shell.css`

### 2026-10-29 — The Pokémon page went blank when the Firestore mirror read failed `bug`
- **Symptom:** offline (or with Firestore unreachable) `/pokemon/:id` showed only its tab strip — no sprite, stats, entry or moves — although the static data and PokéAPI were reachable.
- **Root cause:** `usePokemonDetailData` awaited `getDoc` on the mirror inside the effect's single `try`; its rejection ("client is offline") skipped the static and PokéAPI steps and the whole page stayed empty. `resolvePokemonDetail` already treated the mirror as optional.

### 2026-10-29 — Canon tones used raw as text were illegible in half the themes `dispattern`
- **Symptom:** on the secondary views (meta detail, tournament team, gyms, damage calculator, move lists) Dark/Ghost/Dragon words were ~2:1 on the night surfaces and Electric/Ice/Steel ~1.5:1 on white; gym level badges were white on Electric yellow (1.3:1); PokéPuzzle's correct/present letters were white on `dark`'s mint and amber (1.9 / 1.7:1).
- **Root cause:** a canon colour (type, stat, weather, damage class) is a *fill*; written as `style={{ color: typeColors[t] }}` or `text-[#F08030]` it ignores the theme. And `--color-on-primary` is the ink for the primary only — `dark` sets it to white, so it is wrong on any other bright fill.
- **Fix:** `src/utils/toneInk.js` — `toneInk(tone)` is the tone mixed 45% into `--color-fg` (the `.type-chip` recipe, ≥ 4.6:1 for all 18 types in all ten themes), `toneWash(tone, pct)` its tint; CSS uses the same `color-mix(… 45%, var(--color-fg))`. Letters on success/warning fills take `--color-surface` (≥ 5:1 everywhere).
- **Correct pattern:** a canon tone is a fill, an edge or an icon; as a word it goes through `toneInk`. Text on a fill that is not the primary never uses `--color-on-primary`.
- **Files:** `src/utils/toneInk.js`, `src/components/views/{metaShared,PokemonUsageView,TournamentTeamView,GymsView,DamageCalculatorView}.jsx`, `src/styles/{tools-views,reference-views,pokepuzzle-view}.css`

### 2026-10-24 — The daily data refresh failed every day, after a full scrape `bug`
- **Symptom:** "Refresh competitive data" (`.github/workflows/refresh-data.yml`) red every morning from 2026-10-16 to 2026-10-23, about 16 minutes in; the datasets on main went stale (Enzo, 2026-10-24).
- **Root cause:** the scrape and build succeeded; the commit step then ran `git pull --rebase` with tracked files still modified outside `public/data` (the build rewrites `public/sitemap.xml` with the day's date). Git refuses to rebase over unstaged changes: `error: cannot pull with rebase: You have unstaged changes` — exit 128, nothing pushed.
- **Fix:** after committing `public/data`, `git checkout -- .` drops the other build output (Vercel regenerates it in its own build; `dist/` is ignored and still deploys to Pages), then rebase and push. Reproduced in a throwaway repo: the old step fails with the same error, the new one pushes.
- **Correct pattern:** a CI step that commits part of the tree must leave the rest clean before any rebase or pull. When a scheduled job turns red, read its last log lines before assuming the scrape broke.
- **Files:** `.github/workflows/refresh-data.yml`

### 2026-10-23 — Opening a Pokémon's Competitive tab dropped the app's connection on a phone `perf`
- **Symptom:** in the installed PWA, opening the Competitive tab of a Pokémon from the Pokédex made the app "lose its connections" for a while (Enzo, 2026-10-23).
- **Root cause:** every static-data hook fetched its file in its own effect, per mounted instance. The tab asked for `mega-stones.json` once per sprite (`useMegaStones` inside every `MonSprite`, 36×), `tournaments.json` 3×, `usage-index.json` 2× and `smogon.json` (1.8 MB) twice (`useSmogonData` + `loadSmogon`). Measured in dev (StrictMode doubles it): 89 requests, 7.5 MB at once. That much downloading and parsing on a phone starved Firestore's long-poll channel until it dropped.
- **Why it went unnoticed:** each hook looked correct alone ("fetch once on mount"), and the cost only shows when many components mount at once on a slow connection. Desktop on Wi-Fi never felt it. Some loaders also built the URL without the `?d=` stamp, so even the HTTP cache held two copies.
- **Fix:** `src/services/staticData.js` loads each `public/data` file with one request per session (in-flight promise shared, parsed value kept in memory, retried after a failure); `useStaticData(file)` wraps it for components. Every dataset loader goes through it: `useMegaStones`, `useSmogonData`, `loadSmogon`, `loadCompetitivePreset`, `useTournamentData` (teams prepared once per file), `useUsageIndex`, `useUsageFormat`, `useMoveTypes`, `useCompetitiveUsage`, `useGymLeaders`, `useBattleItems`, `useTrainerSprites`, `useTierLegality`, the share snippet's move types and the mega-stone lookups in `useActiveTeamStore` / `useForumStore`. Same tab after: 8 requests, one per file.
- **Guard:** `src/services/staticData.guard.test.js` fails CI if any other source file fetches a `data/…` URL itself (only `staticData.js` and `pokemonDataCache.js` may). Checked: against the old code it names the offenders.
- **Correct pattern:** load a baked dataset with `useStaticData(file)` in a component or `loadStaticData(file)` elsewhere, never with a `fetch` in a hook's own effect. A hook runs once per mounted component, and a sprite, a card or a row is many components. Before adding a big file to a screen, count what the screen downloads (DevTools → Network, or the request log in `/verify-ui`) on a phone profile, not on desktop Wi-Fi.
- **Files:** `src/services/staticData.js`, `src/services/staticData.guard.test.js`, `src/hooks/useStaticData.js`, the hooks and modules named above

### 2026-10-21 — A saved-teams listener that ran ahead of auth died for the whole session `bug`
- **Symptom:** "Não foi possível carregar seus times salvos" on opening the app, and — where it happened — no saved teams for the rest of that session.
- **Root cause:** `useAuthStore` seeds `userId` from the boot snapshot (last visit's uid) so the shell paints before Firebase answers, and `useFirestoreTeams` starts the listener as soon as `userId` exists. When that runs ahead of the restored session (a stale snapshot, a token still in flight) Firestore answers `permission-denied` — and a listener that errors is dead for good. The error handler toasted and stopped.
- **Fix:** `useFirestoreTeamsStore` now treats `permission-denied` before `isAuthReconciled` as "too early": no toast, it waits for auth to settle and re-binds once (same uid; a changed uid is re-bound by the hook on `userId`). A refusal after that is reported as before. Tests drive auth answering late.
- **Correct pattern:** **a Firestore listener started from a cached identity must survive auth arriving late.** An error callback is the listener's last breath — decide there whether the failure is real or just early, and re-subscribe for the early case rather than reporting it.
- **Files:** `src/store/useFirestoreTeamsStore.js`, `src/store/useFirestoreTeamsStore.test.js`

Inside a card a button is filled (`btn-secondary`), never outlined. Measure nested boxes and page height before and after (the sweep script in the audit).

### 2026-10-21 — Search engines could only ever see the English site `dispattern`
- **Symptom:** Enzo: "acho que não tem pesquisa/índex em ptbr para pesquisas em navegador br". The Google result for pokemonbuilder.app carried the English title and description, for Brazilian searches too, and no Portuguese page appeared in results.
- **Root cause:** the language was a client-side preference only (`navigator.language` + `localStorage`, `useLanguageStore`), so every URL served both languages and none of them said which. Googlebot crawls as en-US with no storage, so it only ever rendered English; `index.html` was fixed at `lang="en"`, `render-meta.js` wrote English titles for every request, and there was no hreflang. On top: the HTML body was an empty `#root` (nothing for a reader that skips JavaScript), no structured data, and the sitemap missed `/challenge`, the item pages and anything about types.
- **Fix:** the language moved into the URL — English at the root, Portuguese under `/pt` (`src/utils/localePath.js`). `LocaleRouter` folds the prefix into the basename, derived from the same location it renders, so no route changed and switching language remounts nothing. One table of titles and descriptions (`src/utils/seoPages.js`, copy in `seo.*`) feeds both `render-meta.js` (now also `lang`, hreflang, `og:locale`, JSON-LD, a prerendered body) and `useDocumentMeta`. The sitemap lists every page in both languages with alternates. Added the type chart (`/types`, `/types/:type`) and the first-visit landing on `/`.
- **Correct pattern:** **a page's language must be readable from its URL alone** — anything a crawler can't put in a request (storage, the browser's language, an account) can only ever pick between URLs, never change what one URL means. And a page title lives in one table read by the server and the client; a view that writes its own title for a route the table knows makes the HTML and the hydrated page disagree. Never change a router's basename as a prop that can lag its location: for one render the router matches nothing and unmounts the app.
- **Files:** `src/utils/localePath.js`, `src/components/LocaleRouter.jsx`, `src/services/localeHistory.js`, `src/store/useLanguageStore.js`, `src/main.jsx`, `src/utils/seoPages.js`, `src/hooks/useDocumentMeta.js`, `api/render-meta.js`, `api/_lib/seoSnapshot.js`, `scripts/build-sitemap.mjs`, `public/robots.txt`, `index.html`, `src/components/views/{TypesView,LandingView,HomeEntry}.jsx`, `docs/modules/seo_and_landing.md`

### 2026-10-20 — A Pokémon holding its Mega Stone never Mega Evolved `bug`
- **Symptom:** a team with a Mega Stone fought as the base Pokémon in both battle types. Enzo: "garantir que os pokemons mega evoluam caso estejam segurando suas mega stones". Found while tracing it: a team saved with the Mega forme as its species (`Charizard-Mega-X`) started the battle already Mega Evolved, with no Mega Evolution moment.
- **Root cause:** four gaps, each one enough. (1) The challenge's `CHOICE_PATTERN` accepted `move N` only, so `move N mega` got a 400. (2) The client never sent it, because no control offered it: the request's `canMegaEvo` was never read. (3) The AI's `legalOptions` never produced it. (4) No Showdown validator runs in either battle, and the validator is what turns a battle-only forme back into its base (`species.battleOnly`).
- **Fix:** `CHOICE_PATTERN` takes ` mega`; `readMyRequest` returns `canMega`; `useBattleCommands` adds a MEGA switch, on by default and reset with every request (the M key toggles it), and sends `move N mega`; the AI Mega Evolves whenever it can (`AI_VERSION` 1.0.1), and `knowledge.js` learns the stone from `-mega`; `toStartingForme` (`api/_lib/battleResolver.js`) starts a battle-only forme as its base, in `validateTeam` (new runs) and in the PvP `setUpState`. The PvP path runs **only for a battle with no published line yet**, because a published battle must replay exactly as it was shown.
- **Correct pattern:** **when no validator runs, the sim takes the paste literally.** Anything the validator would normalise (battle-only formes, levels, clauses) is ours to normalise before the first replay, never after. The service worker is the authority: a visible tab calls `registration.update()` every 60s (and on focus/`online`), which reliably finds a deploy because `sw.js` embeds the hashed precache manifest, so the new worker installs and parks in `waiting` — flipping `needRefresh`, the only state the button trusts. The HTML poll survives *only* as a fallback for pages with no service worker at all (private windows, a failed registration) and stays silent whenever `getRegistration()` returns one. Applying an update never plain-reloads: with a waiting worker it hands over via `updateServiceWorker(true)` (watchdogged), and otherwise `hardReload()` skips waiting, or unregisters, before navigating. The `PATCH_NOTES_VERSION` handler no longer unregisters anything and no longer reloads — reaching that code means the new bundle is *already running*. Measured after: prompt at **+46s**, one click, new build; a version bump costs 1 navigation instead of 2 and keeps its worker.
- **Correct pattern:** **`window.location.reload()` never picks up a new deploy while a service worker with a navigation fallback controls the page.** Leaving the current build means handing over to the waiting worker (skipWaiting → controllerchange) or dropping the registration first. And a user-visible signal must have exactly one detector: two sources racing for one modal means the button cannot know what it is applying, which is how a dead reload hid behind a prompt that "worked the second time".

### 2026-09-09 — The whole app was outline-defined, in all six themes `dispattern`
- **Symptom:** the UI read as busy and boxy no matter how many individual borders were removed. Removing ~40 nested borders from Home barely changed how it felt.
- **Root cause:** measured per theme, **the step from `--color-surface` to `--color-border` was larger than the step from `--color-bg` to `--color-surface`** — in every one of the six. In `dark`, bg→surface was 13 luminance units and surface→border was 22. So a card's *outline* was doing more work than its *fill*, and every region in the app was defined by a line. That is a token-level property: you cannot fix it by deleting borders one at a time, because the ones that remain still dominate.
- **Fix:** rebalanced `--color-bg` / `--color-surface` / `--color-surface-raised` / `--color-border` in all six themes (and their `theme.js` mirror) so the fill step exceeds the line step everywhere — dark surfaces raised, borders pulled back toward their surface. Lines are now whispers and fill separates regions.
- **Correct pattern:** before adding or auditing borders, check the ratio. A region should be legible with its border removed; the border is a refinement, not the definition. There is a check in the tooling notes below — if a theme reports `LINE WINS`, that theme is outline-defined and no amount of per-component border-pruning will make it feel calm.

```bash
# Run from src/. Every theme must print "fill wins".
python3 - <<'EOF'
import re
s=open('index.css').read()
def lum(h):
    h=h.lstrip('#'); r,g,b=(int(h[i:i+2],16) for i in (0,2,4)); return 0.2126*r+0.7152*g+0.0722*b
for blk in re.split(r'(?=:root)', s):
    m=re.search(r"data-theme='(\w+)'", blk)
    if not m: continue
    g=lambda k:(re.search(rf'--color-{k}:\s*(#[0-9a-fA-F]{{6}})',blk) or [None,None])[1]
    bg,su,bo=g('bg'),g('surface'),g('border')
    if not all([bg,su,bo]): continue
    fill=abs(lum(su)-lum(bg)); line=abs(lum(bo)-lum(su))
    print(f"{m.group(1):9} fill {fill:5.1f} line {line:5.1f} {'fill wins' if fill>line else 'LINE WINS'}")
EOF
```

### 2026-06-18 — PokePuzzle crashed with QuotaExceededError after the index migration `bug`
- **Symptom:** `Uncaught DOMException: The quota has been exceeded.` at `PokePuzzleView.jsx` `localStorage.setItem` — the PokePuzzle broke. The save payload itself is tiny (guesses/status/id).
- **Root cause:** the static-index migration enriched `pokemon-index.json` to ~199KB and `loadPokemonIndex` cached it in **localStorage** (`fetchStaticJson` uses `storage: 'local'`, 30-day TTL). The index didn't need to be in localStorage at all — it's already cached by the browser/PWA service worker over HTTP.
- **Fix (two parts):**
  1. **Root:** added `fetchLargeStaticJson` (`storage: 'none'` → memory-only) and pointed `loadPokemonIndex` at it. `getStorage('none')` returns null so nothing hits Web Storage; the index reloads in ~13ms from HTTP cache each session.   2. **Robustness:** wrapped PokePuzzle's `setItem` calls in `safeLocalSet` (try/catch) — Firestore is the real save for logged-in users; a full quota must never crash the game.
- **Correct pattern:** never persist large blobs (>~50KB) in localStorage — it's a tiny shared ~5MB quota; use memory + HTTP/SW cache. Any `setItem` that runs often must be wrapped (storage is best-effort).

### 2026-06-18 — Pokédex "loading gets slow as you scroll" — fat Firestore payload `perf`
- **Symptom (PWA):** scrolling the Pokédex/Team Builder list far down made the "load more" progressively slower (no freeze, just slow loading).
- **Diagnosis (measured, not guessed):** added temporary `[PERF]` instrumentation to `fetchMore`. Findings:
  - **It was NOT the render.** Even with 1246 cards in the DOM, `render+paint` stayed ~120-220ms (`PokemonCard` is `React.memo`, so old cards are skipped). **Virtualization would not have fixed this symptom.**
  - **It WAS the network.** Each batch of 50 docs from `artifacts/pokemonTeamBuilder/pokemons` was **~300KB**, and `getDocs` time **doubled** from ~250ms to ~517ms as the cursor (`startAfter`) went deeper. The list only uses **4 fields** (`id, name, types, sprite`) but each doc carried `moves` (hundreds), `stats`, `abilities`, `evolution_chain_url` — only the detail panel needs those.
  - Firestore web SDK has **no `select()`** (Admin-only), so fields can't be trimmed at the query level.
- **Fix:** the Pokédex list now loads from the **static `public/data/pokemon-index.json`** (the project's preferred data source per CLAUDE.md) instead of Firestore. The index was enriched with `types` + `generation` (`build-pokemon-cache.mjs`), sprites are **derived from the id** (`pokemonSprites.js`, zero stored bytes), and the whole 1025-entry list loads **once** (~199KB / one request, ~6-13ms cached). Filtering/search/pagination became **client-side** (instant). The detail panel still lazy-loads the full doc from Firestore on click (cascade in `PokedexView`). Result: per-batch network went from 250-555ms × 21 round-trips to **one ~13ms load, zero network on scroll**.
- **Cache-invalidation trap (caught in testing):** the data cache stores the index in `localStorage` for 30 days. After changing the index shape, the **old cached index (without `types`) broke the UI** (no type icons, dead filters) until storage was cleared — which real users can't do. **Fix:** bumped `CACHE_VERSION` (`v1`→`v2`) in `pokemonDataCache.js` so the key changes and stale entries are ignored, plus a one-time `purgeStaleCacheVersions()` sweep.
- **Correct pattern:** (1) **measure before optimizing** — the obvious fix (virtualization) was the wrong one; instrumentation pointed at network payload. (2) For large, rarely-changing lists, prefer the **static `public/data/` cache** over Firestore (CLAUDE.md already mandated this; the Pokédex was violating it). (3) **Bump `CACHE_VERSION` whenever cached data shape changes**, or long-TTL users get a broken UI after deploy.
- **Files:** `scripts/build-pokemon-cache.mjs`, `public/data/pokemon-index.json`, `src/services/pokemonDataCache.js`, `src/store/usePokedexStore.js`
