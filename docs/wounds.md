## Resolved wounds

### 2026-09-10 — The phone chrome didn't hug the edges, and the drawer's About block was a web footer in disguise `dispattern`
- **Symptom:** Enzo, iPhone, after the fixed-shell fix: header and tab bar should "encaixar mais na borda do cel" — a visible gap between the status bar and the header row, and under the tab labels above the home indicator; the tab bar should look "mais cara de app". And the credits block in the drawer broke the rail's style: pills wrapping onto a second line, a bordered stepper, a loose credit line.
- **Root cause:** desktop sizing carried into phone chrome. The header band stayed 60px under a status bar that already separates it from the edge; the tab bar added a fixed `--space-2_5` *on top of* the home-indicator inset (~96px total vs iOS's 83pt); a pressed tab painted a rounded fill like a web button. The About block was the footer's own markup (`FooterFeedback` pills, boxed `TextSizeControl`) moved wholesale into a navigation column instead of being rebuilt from the column's parts.
- **Fix:** phone `--app-shell-top-band-height: 3.25rem` (52px); tab bar `padding-block: var(--space-1) max(var(--space-2), env(safe-area-inset-bottom))` with the content reservation derived from the same parts; 24px tab glyphs, 500-weight labels, press = icon `scale(0.88)` with no cell fill. New `DrawerAboutSection`: a folded `ShellNavGroup` of ordinary nav rows (`FooterFeedback variant="drawer"`, "What's new" + version, text size with an `inline` stepper) plus one quiet credit line; dead `.app-shell__drawer-meta*` rules removed. Its open state is local, not in the persisted two-slot `openNavGroups`, which is per user rather than per breakpoint.
- **Verified (Chromium, 390×844):** header 55px (3.25rem at the current UI scale); tab bar 63px without a safe-area inset (~87px expected with an iPhone's 34px, was ~96); 25px tab glyphs, label weight 500, tab transition `color` only; About section folded by default, six rows when open, trailing values 12px from the right edge (the row inset), inline stepper borderless. Drift audits 0/0/0; tests 314/314; AppLayout lint unchanged from HEAD.
- **Correct pattern:**
  - **Phone chrome hugs the edges:** a safe-area inset *is* the padding, not something to add a breath on top of; the header band can be shorter than desktop's because the status bar already frames it.
  - **When content moves between containers, rebuild it from the destination's parts** — a footer's pills in a nav column still look like a footer.
  - **State persisted per user must not be shared by UI that only exists at one breakpoint.**
- **Files:** `src/styles/app-shell.css`, `src/index.css`, `src/components/DrawerAboutSection.jsx`, `src/components/FooterFeedback.jsx`, `src/components/AppLayout.jsx`, `src/constants/translations.js`, `docs/modules/components.md`

### 2026-09-10 — On a real iPhone the header vanished, the drawer cut its own list, and Home stretched forever `bug`
- **Symptom:** Enzo, on the installed PWA after the shell fix above shipped to preview: Meta "quebrou a header" — a ~20px empty band where the title should be (Home too); the drawer "mt mal otimizada" — the list cut off at "My Te…" above a ~250px pinned block of credits; "ainda consigo rolar infinitamente a tela home" — ~440px of blank opening under the last post.
- **Root cause:**
  1. **`100dvh` — this wound's own earlier fix — is wrong in an iOS home-screen app with `viewport-fit=cover`.** It reports the full screen including the status bar, while the web view starts *below* the status bar. The fixed drawer and tab bar sat correctly (they use the real view), but the dvh-sized shell came out ~47px taller than the view, so the document scrolled that much and pulled the sticky header off the top, leaving 64 − ~47px of empty band. Inferred from the device screenshots (the fixed drawer starts exactly at the status-bar edge); desktop devtools cannot show it.
  2. The drawer-meta block moved out of the footer was placed in `.app-shell__sidebar-bottom`, which is **pinned** — it took ~250px off the scrolling list.
  3. The root scroller had `overscroll-behavior: contain`, which stops chaining but still rubber-bands on iOS; with the document also scrollable, a pull at the bottom kept stretching. The first `none` override then **silently lost** to `.custom-scrollbar`'s `contain` (same specificity, loaded later) — the computed value was still `contain`.
  4. Found on the way, pre-existing: the phone Feed was `calc(100dvh - 5.75rem)`, which never subtracted the tab bar — composer bottom at 833px, tab bar top at 777px, content not scrollable — so the input was unreachable behind the bar.
- **Fix:** `.app-shell { position: fixed; inset: 0 }` and `.app-shell__content { height: 100% }`; `overscroll-behavior-y: none` on the compound `.app-shell__content.custom-scrollbar`; drawer meta moved inside `<nav class="app-shell__nav">` so it scrolls with the list, mobile nav rows 40px with tighter section gaps, account label sentence case; Feed fills through `flex: 1 1 0; min-height: 0` down body → page frame → forum view.
- **Verified (Chromium, 390×844):** shell fixed at 844px, document scrollable 0, root overscroll `none`; Meta header at top 0 before and after scrolling; drawer shows 12 of 19 rows before scrolling (the iPhone showed ~9, then cut), credits inside the scrolling nav; Feed composer bottom 771 < tab bar 777 with nothing to scroll. **Not verified on a device:** the WebKit build in the Playwright cache matches none of the installed playwright-core versions, and home-screen status-bar behaviour can't be emulated anyway.
- **Correct pattern:**
  - **The app frame is pinned (`position: fixed; inset: 0`), never measured in vh or dvh.** Inside it, fill through layout. A `calc(100dvh - X)` is a guess about everything above and below it.
  - **Check mobile fixes on the installed PWA, not only in a browser tab** — home-screen apps have their own viewport rules.
  - **After overriding a property, read its computed value.** A same-specificity utility class loaded later wins without a sound.
  - **A pinned drawer footer holds one row (the account).** Anything longer scrolls with the list.
- **Files:** `src/styles/app-shell.css`, `src/styles/forum-view.css`, `src/components/AppLayout.jsx`, `.claude/skills/design-system/SKILL.md`

### 2026-09-10 — Phone lists ran 12,000–30,000px, and thumbs were aiming at 17–28px controls `dispattern`
- **Symptom:** after the shell fix, a 14-route sweep at 390px found no horizontal overflow anywhere — but Tournaments scrolled **30,189px** (40 featured + 80 tournament cards at one column, 720 sprites loaded up front) and Meta **12,017px**, with "Duplas comuns" / "Trios comuns" stacked under the *entire* ranking. Secondary controls were sized for a cursor: Meta source links 17px tall, timeline reply 19px, like 21px, avatar pencil 21px, partner-card button 25px, the condensed composer's Save 25px, "Criar seu primeiro time" 27px, Grade/Lista 27px, card stars 22–28px. Home's daily teaser cut "Quem é esse Pokémon? Teste seus conhecimentos!" at 148 of 237px. And every Tailwind `hover:` state stayed on after a tap.
- **Root cause:** desktop layouts reused unchanged as phone layouts. A grid that is a screen or two across five columns becomes one column on a phone and multiplies its own height; a control sized for a cursor keeps that size for a thumb; and `hover:` has no "off" on touch.
- **Fix:** `useProgressiveReveal` + `ShowMoreButton` render long lists in pages below `lg` (gated by the new `useMediaQuery(maxWidthBelow('lg'))`; the math is the pure, tested `getRevealState`): Meta 12 then +24, reset by format/sort/search; Tournaments 4 featured / 6 tournament then +10, reset by search. `.touch-target` (index.css, coarse pointer only) extends the **hit area** with an invisible `::after` instead of growing the control, with `--y` for segmented buttons that touch; per-class `::after` where the control is absolutely positioned or styled in CSS (home buttons, forum actions, card stars, compact Save). Primary `.home-button` is 44px on touch. `touch-action: manipulation` on controls. Tailwind `future.hoverOnlyWhenSupported`; the one control hidden until hover (onboarding remove badge) gets `[@media(hover:none)]:opacity-100`. The teaser wraps.
- **Verified at 390px:** Meta 12,017 → 2,431px, pairs heading at 1,448px, "Ver mais (126 restantes)" → 36 cards; Tournaments 30,189 → 2,874px and 720 → 60 images; teaser untruncated. Tests 314/314 (5 new); lint counts unchanged from HEAD.
- **Correct pattern:**
  - **When a desktop grid collapses to one column, multiply its height by the column count before shipping.** Past ~3 screens on a phone, page it (`useProgressiveReveal`) — and never stack a secondary section under an unbounded list.
  - **Grow the hit area, not the control.** `.touch-target` / a per-class `::after` under `(pointer: coarse)`. Never put the utility on an absolutely positioned element; it resets it to `relative`.
  - **Nothing may be visible only on hover.** Hover is gated to hover-capable devices now, so `opacity-0 group-hover:opacity-100` is *permanently hidden* on a phone. Give it a `[@media(hover:none)]:` state, or don't hide it.
- **Files:** `tailwind.config.js`, `src/index.css`, `src/hooks/useMediaQuery.js`, `src/hooks/useProgressiveReveal.js`, `src/utils/progressiveReveal.js` (+ test), `src/components/ShowMoreButton.jsx`, `src/components/views/MetaUsageView.jsx`, `src/components/views/TournamentsView.jsx`, `src/components/views/HomeView.jsx`, `src/components/views/AllTeamsView.jsx`, `src/components/views/metaShared.jsx`, `src/components/modals/TeamBuilderOnboardingModal.jsx`, `src/styles/home-view.css`, `src/styles/forum-view.css`, `src/styles/team-builder-view.css`, `src/constants/translations.js`

### 2026-09-10 — On a phone the app scrolled like a website: a `100vh` shell, a 191px footer, and boxes eating the width `bug`
- **Symptom:** Enzo, from a phone: scrolling to the bottom of Home was "confusa e desagradável"; the app "ainda não transparece mobile first" — "rolagem demais e sensação de mole, como rolar além da tela tipo website", broken buttons, Pokédex icons hidden, dead space. Measured at 390×844: the Pokédex placeholder cut mid-word ("Pesquisar Poké"), the second type icon clipped on every dual-type card, a ~50px blank band under the Meta header, and Meta's lead paragraph truncated at "clique em um…".
- **Root cause:** five separate things, all invisible on a desktop viewport:
  1. **The shell itself was `height: 100vh`** (`.app-shell`, `.app-shell__content`). The 2026-09-09 wound had already taught that `100vh` is the *large* viewport on mobile — but only the modal learned it. The one scroll container in the app was ~90px taller than the visible screen, so its bottom sat below the fold: the page literally kept going after the screen ran out.
  2. **The site footer ran on phones.** 191px — 23% of the screen, 34 elements — of credit, likes, suggestion, disclaimer, version, text size and social links at the end of *every* page's scroll. Reaching the bottom of a page meant leaving the app for a website.
  3. **Nothing stopped the document from rubber-banding.** The body never scrolls, but a phone still bounces the document on a drag, dragging header and tab bar with it. And with no `viewport-fit=cover`, `env(safe-area-inset-bottom)` was always 0, so the tab bar's inset reservation never did anything.
  4. **Pokédex: boxes inside boxes cost the width.** The search sat in a bordered `team-builder-panel p-4`, and the grid in another — 34px of width each, spent drawing lines. The card header then had to fit id + two type icons + a ringed favourite button in 91px: it needed 98 (and at 360px wide it is 6px short even without the panels). The overflow clipped the types; letting the id truncate instead just produced "#00…".
  5. **Meta: double gutter and a clamp.** The view added its own `px-3 py-4` inside `.app-shell__body`'s gutter (text 12px off the page edge, padding stacked under the header), `line-clamp-2` on a sentence longer than two lines, a regulation select that wrapped alone onto a right-aligned row, ALL-CAPS section headings, and `hover:-translate-y-0.5` on cards — which on touch *sticks* after a tap.
- **Fix:** `height: 100vh; height: 100dvh` on both shell layers (body never scrolls, so the URL bar never collapses and `dvh` never reflows). Below 1024px `.app-shell__footer` is `display: none` and its contents render in the drawer tail (`.app-shell__drawer-meta`); desktop footer unchanged. `FooterFeedback`'s two dialogs are now `createPortal`ed to `<body>` — rendered inside the drawer they would have been trapped by its `transform`, which makes a transformed ancestor the containing block for `position: fixed`. `html, body { overscroll-behavior: none }`; `viewport-fit=cover` with side insets returned on the scroller, drawer and tab bar; tab bar is non-selectable with no touch callout; mobile body padding `--space-4 / --space-6`. Pokédex: no panels; search in a sticky band under the header (bleed via spread `box-shadow` + `clip-path`, no layout cost); short placeholder `pokedex.searchPlaceholderShort` ("Nome ou nº" / "Name or #" — "Buscar nome ou nº" still overflowed at 360px); cards on `--color-surface` scoped to `.pokedex-mobile-grid` (raised-on-bg is invisible in light: `#f6f6f7` on `#f2f2f3`). Card header is **type icons only**: the favourite star moved onto the sprite box's corner as a 28px target, and — at Enzo's direction — the number moved to the right of the name, unpadded (`#5`, not `#0005`), with the name as the side that truncates. Meta: no own padding on phones, no clamp (the how-to clause is `sm:` only), select first and full-width, sort group `self-stretch` to the field's height, sentence-case headings, `transition-colors` with no lift. `SourceCredit` label lost its caps and stacked opacity.
- **Verified at 390×844:** footer hidden and page bottom flush with the tab bar top (777 = 777); placeholder 163px in 170px available; search 208 → 244px; cards 103 → 110px; 0 clipped type icons, 0 truncated numbers and 0 truncated names over 50 cards (at 360px: 0 / 0 / 3 — butterfree, jigglypuff, wigglytuff — with placeholder 96px in 140px and no horizontal overflow); search band stuck flush under the header (64 = 64); Meta header→text gap ~50 → 17px, text untruncated, search and sort sharing exact top/bottom edges. Lint counts on touched files identical to HEAD; 309/309 tests; drift audits 0/0/0.
- **Correct pattern:**
  - **Measure a mobile change at a phone viewport, never infer it from a desktop one.** Every item above was fine at 1440px. And `vh`/`dvh` differences don't show in desktop devtools at all — reason about them from the spec.
  - **`100vh` is banned for anything sized to the screen**, including the shell. Grep for it: `grep -rn "100vh" src/styles src/index.css`. Remaining uses in `team-builder-view.css`, `forum-view.css`, `generation-quiz-view.css`, `secret-room-guesser.css` are the next candidates.
  - **A phone page ends where its content ends.** Site chrome (credits, legal, social) goes in the drawer, not under every page.
  - **`position: fixed` UI must portal to `<body>`** if its component can ever render inside a transformed ancestor (the drawer, a sheet, anything animated with `transform`).
  - **On a phone, width is the scarcest resource.** A bordered wrapper costs `2 × (padding + border)`; before adding one, check what the children lose. And no `hover:` transform on touch-reachable cards — hover sticks after a tap.
- **Files:** `index.html`, `src/index.css`, `src/styles/app-shell.css`, `src/styles/team-builder-view.css`, `src/components/AppLayout.jsx`, `src/components/FooterFeedback.jsx`, `src/components/views/PokedexView.jsx`, `src/components/views/MetaUsageView.jsx`, `src/components/views/metaShared.jsx`, `src/constants/translations.js`

### 2026-09-10 — The sidebar hid its own navigation behind an accordion, and dimmed the labels that were left `dispattern`
- **Symptom:** the expanded rail was the brand, four pinned links, **four identical chevron rows**, and ~400px of nothing. Everything past the pinned four was invisible and two clicks away, and every label that *was* visible sat at `--color-muted`, so the only legible row on the rail was the active one.
- **Root cause — two decisions that each made sense alone and compounded:**
  1. **The accordion (`openNavGroup`, at most one section open).** It was added to stop the rail growing to whatever the user last left open, and it worked: it kept the rail *empty*. A closed section is a row that costs a full nav row of height and offers no destination, so four of them turned 15 links into 4 chevrons — and those chevrons read as four more things to click, competing with the four real destinations above them. It also carried a persisted localStorage key, a route-follows-fold effect, and a "current page is in a folded section" dot, all to manage state that only existed because the fold existed.
  2. **`.app-shell__nav-link { color: var(--color-muted) }`.** Muting the whole row muted the *label*, not just the icon. Hierarchy that costs you the ability to read your own navigation is not hierarchy.
- **Fix — a cap, not a mode.** Folding stays; **at most two sections are open at once** (`MAX_OPEN_NAV_GROUPS`), and opening a third closes the least recently opened. That is the state neither failure can reach: the rail always shows part of the tail, and its height stays inside a known band. `openNavGroups` is an ordered oldest-first list, so eviction is a `slice(-2)`; a click and "you navigated into a folded section" both append through one `withGroupOpen` helper, so they cannot disagree about what gets dropped. First run opens two by default — landing on an empty rail is the whole thing being avoided. The row sits at `--color-fg` and **the icon** carries the de-emphasis at `--color-muted`, coming up to foreground on hover and on the active row. Rows tightened to `min-height: 2rem`; with two sections open the nav does not scroll at all at 900px. Active is a fill and nothing else — the weight bump came off, since a foreground row plus one fill is already unambiguous when exactly one item is ever selected.
- **The alignment bug this uncovered:** the section label's `padding-inline` was hard-coded to `--space-2_5` while the nav row's came from a mobile override at `--space-3`. On a phone the label's first letter sat **4px left of the column of icons under it** — the "nearly aligned" failure the design system names as the most damaging thing on a page. Both now read one `--app-shell-row-inset` variable declared on `.app-shell`, so a responsive override moves the pair. Measured at 390px and 1440px: delta < 0.01px.
- **Correct pattern:**
  - **A sidebar earns its width by showing where you can go.** Before hiding navigation to keep a rail short, check what the rail looks like with everything hidden — "short" and "empty" are the same measurement and very different results.
  - **When two states are both wrong, the fix is usually a bound, not a third mode.** "All folds independent" and "exactly one open" are the extremes of one dial; capping it at two got the property each was reaching for without either's failure. Bound the state, and let the control stay a plain toggle that never refuses a click.
  - **A default is a design decision, not a fallback.** The accordion's rules were fine; it was defaulting to *everything closed* that emptied the rail. Ask what the first run looks like before shipping a persisted preference.
  - **Mute the icon, not the label.** In a two-part row the glyph is what should recede. Twenty full-strength icons are a texture; twenty muted labels are unreadable navigation.
  - **A shared edge needs a shared variable.** Two rules that must resolve to the same inset will drift the moment one gets a responsive override. Name the value once.
  - **State that exists only to manage a fold disappears with the fold.** Removing the accordion removed a localStorage key, an effect, and a dot — none of which were carrying information about the app.
- **Files:** `src/components/ShellNavGroup.jsx`, `src/components/AppLayout.jsx`, `src/styles/app-shell.css`

### 2026-09-10 — The forum put a navigation block where the conversation should be `dispattern`
- **Symptom:** "a tela de fórum tá pouco otimizada em móbile, com campos meio apertados e não claros como interagir." The phone screenshot shows why: a fixed band at the top holding a title row, a search field, four category chips and a two-row topic list, with the thread squeezed into what was left.
- **Root cause — the phone was given the desktop layout, compressed:**
  1. **`.forum-sidebar { height: 175px }` with `.forum-topics-list { max-height: 85px }`.** Below 640px the two-column desktop layout was stacked rather than replaced, so ~23% of a 746px screen was permanently spent on navigation *while reading a thread*. The 85px list showed two rows with no scrollbar and no cut-off row, so nothing said it was a list you could scroll — that is the "não claro como interagir" exactly.
  2. **Tap targets at half size.** The like / reply / delete row was four different ad-hoc Tailwind pills at `py-0.5` on 11px text — **20px tall**, against the ~44px a thumb needs. The composer's controls were `1.85rem` (29.6px) boxes holding the 16px text the iOS zoom guard forces globally, so the field was cropping its own content.
  3. **Delete sat one thumb-width from Reply**, in a row with no separation between a routine action and a destructive one.
  4. Two of those pills wrote raw `red-500` — a colour that does not follow the theme, which the design system forbids outright.
- **Fix:** below 640px the sidebar and the thread are **two screens, not two bands of one screen** — `.forum-view.is-pane-topics` / `.is-pane-thread` show exactly one, with a back control in the thread header (`.forum-main__back`, hidden from 640px up where the list is already visible beside the thread). Measured at 390×844: the topic list goes from **85px to 622px** with 47px rows, and the message list from ~430px to **603px**. One `.forum-msg-action` vocabulary replaces the four pills — filled not outlined, `--color-danger` not `red-500`, 34px tall on a phone, with Delete pushed to the far end of the row (`margin-left: auto`, 149px from Reply at 390px). Composer controls go to 2.25rem on a phone. Desktop keeps both panes and gains breathing room: topic rows `--space-1` → `--space-1_5`, titles 0.75 → 0.8125rem, chips 0.675 → 0.75rem.
- **The trap this fix walked into, and the guard:** hiding a pane with `display: none` **resets its `scrollTop` to 0**, so returning to the thread would have landed it at the top — re-opening the wound of 2026-09-10 ("Forum threads opened at the top") in a new way, from CSS rather than from a hook. `useChatAutoScroll` gained a `pinKey`: when it changes, jump to the bottom and run the existing settle pin. `FeedView` passes the pane.
- **Correct pattern:**
  - **A phone is not a narrow desktop.** When a two-pane layout does not fit, replace it with a flow between two screens; do not stack both and shrink each until they technically fit. A pane compressed to two rows costs the space of a pane and does the job of nothing.
  - **A list must look like a list.** Fixed heights that happen to land between rows hide the one cue that says "there is more here" — either show a clipped row or let it scroll to the pane edge.
  - **A destructive control belongs at the opposite end of the row from the routine ones**, not next in line after them.
  - **`display: none` is not free for a scroll container.** Anything that hides and restores a scrollable region owns re-establishing its position.
  - **Repeated ad-hoc Tailwind pills are a component that was never written.** Four near-identical class strings is how a raw `red-500` gets in and how a 20px tap target survives review.
- **Files:** `src/components/views/FeedView.jsx`, `src/hooks/useChatAutoScroll.js`, `src/styles/forum-view.css`

### 2026-09-10 — The battle header shoved its own controls off screen, and the sync poll fought the player `bug`
- **Symptom:** "header da batalha… o layout tá meio feio e desorganizado" with a phone screenshot: the back button at full width, the opponent's format line wrapping to three lines, and **Discard** clipped mid-word at the right edge. Separately, the same screen was reported as not fluid. And on Home, three saved teams filled the phone screen on their own.
- **Root cause — three:**
  1. **A flex row let the wrong child win the width.** `.battle-nav-bar` had no CSS of its own — just Tailwind `flex items-center justify-between` — so back button, opponent identity and Discard all sized to content. The format line ("gen9randombattle · six random Pokémon, levels balanced by tier") had no `min-width: 0` and no truncation, so it refused to shrink, wrapped to three lines, and pushed Discard past the viewport. Measured at 390px: nav bar **153px tall**, Discard's right edge at **173px** of an element that should have ended at 378.
  2. **The background nudge raised the same flag as a real turn.** `isResolvingTurn` is a store flag that disables every move and switch button. It was set by *every* call to `submitChoice` — including the two that nobody asked for: a 5s poll, and a probe effect whose dependency array contained `myLog.length`, so it POSTed to the serverless resolver **every time a line landed in the log**. The grid went dead for a round-trip every few seconds. The poll also ran flat-out in a hidden tab and never probed on return, so coming back to the battle meant waiting out the rest of an interval.
  3. **One card shape for two jobs.** `.hd-continue-card` is a tall centred column — right for the three-across layout above 34rem, wrong as the *base*, which is what a phone gets: name, count and a 2rem roster stacked with `--space-4` padding, ~122px each, three of them before anything else on Home was reached.
- **Fix:**
  1. `.battle-nav-bar` is a real component: `grid-template-columns: auto minmax(0, 1fr) auto`, so only the middle column is elastic and only it may shrink. Both text lines are single-line and elide. Under 640px the two controls keep their icons and drop their labels — the name in the middle is the part that identifies the battle. Same phone: **38px tall**, Discard's right edge at 378 of 390.
  2. `submitChoice` takes `{ silent: true }`: it leaves `isResolvingTurn` alone and swallows failures. Every background nudge uses it; the manual Sync button spins its own local state. The probe effect no longer depends on `myLog.length` (the question "did I answer round N?" only has a new answer when the round changes), and the poll backs off — 4s, 8s, 15s, 30s, 60s — pausing entirely while the tab is hidden and probing immediately on return. Ten minutes on the battle screen went from **120 serverless calls to seven**.
  3. `.hd-continue-card`'s base is now a **row** — name and count left, roster right — and the tall card is restored inside the existing `@container (min-width: 34rem)` block. 122px → **58px** per team on a phone; desktop unchanged.
  - Two design-system violations in the same view, both by the book: `.battle-panel__title` was ALL CAPS at 0.12em tracking (the rule keeps caps for tiny pill badges only) and is now sentence case, size up / weight down; `.battle-turn-banner` had a border inside `.battle-panel`'s border and now separates by fill, with the "your turn" state carrying `--ring-primary` inside its existing glow keyframe.
- **Correct pattern:**
  - **A bar of three things is a grid, not a flex row.** Flex lets every child argue for width; a grid says which single column is allowed to absorb and give back. Any text in that elastic column needs `min-width: 0` and an ellipsis or it will win an argument it should lose.
  - **A busy flag set by a background poll is a bug, not a nicety.** If a flag disables controls, only a user-initiated action may raise it. Give polls a silent path — separate the "I am doing what you asked" state from "I am checking on my own".
  - **Never put a live value in a dependency array to keep something fresh** when what you need is its value at call time — that turns a once-per-state request into once-per-change. A ref reads current without re-subscribing.
  - **A responsive component's base shape should be its narrow shape.** Writing the wide card first and treating narrow as a fallback is how a phone inherits a layout designed for a third of a desktop column.

### 2026-09-09 — Three mobile dead ends: a picker behind a sheet, a crushed invite, a guide that never learned `bug`

### 2026-09-09 — The whole app was outline-defined, in all six themes `dispattern`
- **Symptom:** the UI read as busy and boxy no matter how many individual borders were removed. Removing ~40 nested borders from Home barely changed how it felt.
- **Root cause:** measured per theme, **the step from `--color-surface` to `--color-border` was larger than the step from `--color-bg` to `--color-surface`** — in every one of the six. In `dark`, bg→surface was 13 luminance units and surface→border was 22. So a card's *outline* was doing more work than its *fill*, and every region in the app was defined by a line. That is a token-level property: you cannot fix it by deleting borders one at a time, because the ones that remain still dominate.
- **Fix:** rebalanced `--color-bg` / `--color-surface` / `--color-surface-raised` / `--color-border` in all six themes (and their `theme.js` mirror) so the fill step exceeds the line step everywhere — dark surfaces raised, borders pulled back toward their surface. Lines are now whispers and fill separates regions.
- **Correct pattern:** before adding or auditing borders, check the ratio. A region should be legible with its border removed; the border is a refinement, not the definition. There is a check in the tooling notes below — if a theme reports `LINE WINS`, that theme is outline-defined and no amount of per-component border-pruning will make it feel calm.

```bash
# Run from src/. Every theme must print "fill wins".
python3 - <<'EOF'
import re
s=open('index.css').read()
def lum(h):
    h=h.lstrip('#'); r,g,b=(int(h[i:i+2],16) for i in (0,2,4)); return 0.2126*r+0.7152*g+0.0722*b
for blk in re.split(r'(?=:root)', s):
    m=re.search(r"data-theme='(\w+)'", blk)
    if not m: continue
    g=lambda k:(re.search(rf'--color-{k}:\s*(#[0-9a-fA-F]{{6}})',blk) or [None,None])[1]
    bg,su,bo=g('bg'),g('surface'),g('border')
    if not all([bg,su,bo]): continue
    fill=abs(lum(su)-lum(bg)); line=abs(lum(bo)-lum(su))
    print(f"{m.group(1):9} fill {fill:5.1f} line {line:5.1f} {'fill wins' if fill>line else 'LINE WINS'}")
EOF
```

- **Root cause:** Colors were hardcoded as a Tailwind class map keyed by stat name (`{ hp: 'bg-red-500', attack: 'bg-orange-500', … }`). Tailwind compiles these to fixed `rgb()` values at build time — there is no runtime hook for theming.
- **Fix:** Added six stat color tokens to `:root` in `src/index.css` (`--stat-hp`, `--stat-atk`, `--stat-def`, `--stat-spa`, `--stat-spd`, `--stat-spe`). `StatBar.jsx` now uses a `STAT_VAR` lookup map (`{ hp: '--stat-hp', … }`) and applies color via `style={{ backgroundColor: \`var(${STAT_VAR[stat] ?? '--stat-hp'})\` }}`. Remaining text/background classes use `var(--color-fg)` / `var(--color-surface-raised)`.
- **Correct pattern:** Per-entity colors (stats, types, rarities) are design tokens that belong in `index.css` as CSS custom properties, not Tailwind utility classes. Tailwind classes are for layout and spacing; CSS variables are for themeable color values.
- **Files:** `src/components/StatBar.jsx`, `src/index.css`

### 2026-06-19 — TypeBadge used inline `style` for type colors instead of CSS classes `dispattern`
- **Symptom:** Type badges always showed game-canonical colors regardless of theme. The inline `style={{ backgroundColor: typeColors[type] }}` bypassed the CSS cascade entirely, making any future theme-layer override impossible and breaking the architectural rule that all color comes through CSS custom properties or static classes.
- **Root cause:** Colors were applied inline using the `typeColors` map (from `src/constants/types.js`), reasoning that type colors are "canonical" and don't change per theme. True — but inline styles are still the wrong delivery mechanism because they can't be overridden by CSS layers, media queries, or forced-colors mode.
- **Fix:** Added 20 `.type-badge--{type}` static CSS classes to `src/index.css` (game-accurate hex values, `color: #fff`). `TypeBadge.jsx` now does `className={\`type-badge--${typeLower}\`}` and has no `style` prop at all. Removed the `typeColors` import from the component.
- **Correct pattern:** Never use inline `style` for colors that come from a known discrete set. Even when values are static/canonical, put them in CSS classes — they stay overridable and are easier to inspect in DevTools.
- **Files:** `src/components/TypeBadge.jsx`, `src/index.css`

### 2026-06-18 — PokePuzzle crashed with QuotaExceededError after the index migration `bug`
- **Symptom:** `Uncaught DOMException: The quota has been exceeded.` at `PokePuzzleView.jsx` `localStorage.setItem` — the PokePuzzle broke. The save payload itself is tiny (guesses/status/id).
- **Root cause:** the static-index migration enriched `pokemon-index.json` to ~199KB and `loadPokemonIndex` cached it in **localStorage** (`fetchStaticJson` uses `storage: 'local'`, 30-day TTL). That + existing cached data filled the ~5MB localStorage quota, so the next `setItem` anywhere (PokePuzzle's frequent autosave) threw. The index didn't need to be in localStorage at all — it's already cached by the browser/PWA service worker over HTTP.
- **Fix (two parts):**
  1. **Root:** added `fetchLargeStaticJson` (`storage: 'none'` → memory-only) and pointed `loadPokemonIndex` at it. `getStorage('none')` returns null so nothing hits Web Storage; the index reloads in ~13ms from HTTP cache each session. Also extended `purgeStaleCacheVersions` to drop any previously-persisted `:static:pokemon-index.json` so existing users' bloated storage self-heals on next load.
  2. **Robustness:** wrapped PokePuzzle's `setItem` calls in `safeLocalSet` (try/catch) — Firestore is the real save for logged-in users; a full quota must never crash the game.
- **Correct pattern:** never persist large blobs (>~50KB) in localStorage — it's a tiny shared ~5MB quota; use memory + HTTP/SW cache. Any `setItem` that runs often must be wrapped (storage is best-effort).
- **Files:** `src/services/pokemonDataCache.js`, `src/components/views/PokePuzzleView.jsx`

### 2026-06-18 — Adding to team crashed after the static-index migration `bug`
- **Symptom (production):** `TypeError: can't access property 0, s.abilities is undefined` in `handleAddPokemon` when adding a Pokémon to a team. Only the Team Builder was affected; the Pokédex was fine.
- **Root cause:** the static-index migration (see wound above) made the list carry only **lightweight** data (`id, name, types, sprite`). But `handleAddPokemon` (and the editor modal) read `pokemon.abilities[0].name`, `pokemon.moves.slice(...)` — fields that no longer exist on the light object. The Pokédex survived because it only reads `types`.
- **Fix:** added `resolvePokemonDetail(id)` to `pokemonDataCache.js` — a cascade (Firestore mirror → static detail → PokéAPI, normalized to the fat shape). `handleAddPokemon` is now `async` and lazily resolves the full record on add when the incoming object is light, then builds the member. Also hardened the editor modal against missing fields (`pokemon.moves || []`, `pokemon.abilities || []`, `pokemon.stats?.[i]?.base_stat ?? 0`).

### 2026-06-18 — Pokédex "loading gets slow as you scroll" — fat Firestore payload `perf`
- **Symptom (PWA):** scrolling the Pokédex/Team Builder list far down made the "load more" progressively slower (no freeze, just slow loading).
- **Diagnosis (measured, not guessed):** added temporary `[PERF]` instrumentation to `fetchMore`. Findings:
  - **It was NOT the render.** Even with 1246 cards in the DOM, `render+paint` stayed ~120-220ms (`PokemonCard` is `React.memo`, so old cards are skipped). **Virtualization would not have fixed this symptom.**
  - **It WAS the network.** Each batch of 50 docs from `artifacts/pokemonTeamBuilder/pokemons` was **~300KB**, and `getDocs` time **doubled** from ~250ms to ~517ms as the cursor (`startAfter`) went deeper. The list only uses **4 fields** (`id, name, types, sprite`) but each doc carried `moves` (hundreds), `stats`, `abilities`, `evolution_chain_url` — only the detail panel needs those.
  - Firestore web SDK has **no `select()`** (Admin-only), so fields can't be trimmed at the query level.
- **Fix:** the Pokédex list now loads from the **static `public/data/pokemon-index.json`** (the project's preferred data source per CLAUDE.md) instead of Firestore. The index was enriched with `types` + `generation` (`build-pokemon-cache.mjs`), sprites are **derived from the id** (`pokemonSprites.js`, zero stored bytes), and the whole 1025-entry list loads **once** (~199KB / one request, ~6-13ms cached). Filtering/search/pagination became **client-side** (instant). The detail panel still lazy-loads the full doc from Firestore on click (cascade in `PokedexView`). Result: per-batch network went from 250-555ms × 21 round-trips to **one ~13ms load, zero network on scroll**.
- **Cache-invalidation trap (caught in testing):** the data cache stores the index in `localStorage` for 30 days. After changing the index shape, the **old cached index (without `types`) broke the UI** (no type icons, dead filters) until storage was cleared — which real users can't do. **Fix:** bumped `CACHE_VERSION` (`v1`→`v2`) in `pokemonDataCache.js` so the key changes and stale entries are ignored, plus a one-time `purgeStaleCacheVersions()` sweep.
- **Correct pattern:** (1) **measure before optimizing** — the obvious fix (virtualization) was the wrong one; instrumentation pointed at network payload. (2) For large, rarely-changing lists, prefer the **static `public/data/` cache** over Firestore (CLAUDE.md already mandated this; the Pokédex was violating it). (3) **Bump `CACHE_VERSION` whenever cached data shape changes**, or long-TTL users get a broken UI after deploy.
- **Files:** `scripts/build-pokemon-cache.mjs`, `public/data/pokemon-index.json`, `src/services/pokemonDataCache.js`, `src/store/usePokedexStore.js`

### 2026-06-18 — First security rules broke likes + admin panel `security` `bug`
- **Symptom (production):** `Error listening to likes: Missing or insufficient permissions`, `Failed to toggle like`, and `Error loading suggestions` in the admin panel — after publishing the first cut of `firestore.rules`.
- **Root cause:** the initial rules were derived only from `src/store/*.js` and missed three real access patterns:
  1. **Likes** live at `artifacts/{appId}/feedback/likes` (a shared counter doc in `FooterFeedback.jsx`) — needs public read + signed-in self-toggle, but the generic `feedback/{docId}` rule made it admin-read/create-only.
  2. **Admin reads suggestions** but the rule required `email_verified == true`; the app's `isAdmin` (email-only) does not, so an unverified admin token was denied. (Kept the stricter rule per Enzo's choice — admin account must be email-verified in Firebase Auth.)
  3. **Admin cross-reads other users' `users/{uid}/profile/preferences`** for display names — blocked by the owner-only `users/{userId}/**` rule.
- **Fix:** added a specific `match /feedback/likes` (public read; `create,update` allowed only when the write adds/removes **only the caller's own uid** via `touchesOnlyOwnLike()`), and a `match /users/{userId}/profile/{docId}` allowing `read` by owner **or** admin. Firestore OR's overlapping matches, so these widen access without weakening the base rules.
- **Correct pattern:** rules must be derived from **every** Firestore call site, not just stores — grep `src/` for `collection(`/`doc(` (`FooterFeedback.jsx`, views, etc.). Any path the app touches but rules don't match = denied in production. Test admin + anon + signed-in paths in the Rules Playground before publishing.
- **Files:** `firestore.rules`

### `dispattern` — 32 silently-swallowed `catch` blocks
- `grep -rn "catch (_)\|/* ignore */" src/` → ~32 hits. Many are legitimate (localStorage/JSON guards), but some swallow Firestore/network errors with no user feedback and no `console`.
- **Correct pattern:** for anything user-initiated (save team, post message, sign in), surface failures through `useToastStore`. Reserve silent catches for genuinely optional reads (storage, parsing) and comment *why*.

- **Correct pattern:** route real errors to toasts/telemetry; delete debug logs before committing. Consider an eslint `no-console` rule (warn) once the backlog is cleared.

### `dispattern` — Unprotected `localStorage.setItem` across stores
- Several stores call `localStorage.setItem` with no try/catch: `useLanguageStore`, `useAuthStore` (streak/greeting/syncPrompt), `useThemeStore`, `useQuizRunsStore`. Each payload is tiny, but a full quota throws and could crash whatever runs it. PokePuzzle was hardened (2026-06-18) after a real QuotaExceededError; the rest weren't, to keep that fix focused.
- **Correct pattern:** wrap any `setItem` in try/catch (storage is best-effort). Consider a shared `safeLocalSet` util. Found 2026-06-18.

### `dispattern` — Duplicated "resolve fat pokémon detail" cascades
- The same fallback (Firestore mirror → static detail → PokéAPI) now exists in **three** places: `AppLayout.fetchPokemonDetails`, the `PokedexView` detail effect, and the new `resolvePokemonDetail` in `pokemonDataCache.js`. They drifted slightly (different normalization).
- **Correct pattern:** consolidate the others onto `resolvePokemonDetail` (the service is the right home per CLAUDE.md). Not done yet to keep the team-builder fix small. Found 2026-06-18.

### `dispattern` — Very large view components
- `PokedexView.jsx` (~2074 loc), `HomeView.jsx` (~1338), `PokePuzzleView.jsx` (~1630), `RandomGeneratorView.jsx` (~1263), `AppLayout.jsx` (~1149). Hard to review, easy to regress.
